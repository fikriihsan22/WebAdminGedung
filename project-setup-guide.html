1. What exists today

This repository is an early MVP foundation rather than a finished admin dashboard. The browser currently renders the starter content from src/app/page.tsx. The meaningful application foundation is already present in the package setup, styling system, typed database contract, and project scripts.

Important: the database model is ahead of the UI. That is useful: the next feature can be implemented vertically—from one route, to one query, to one form—without redesigning the foundation.

How a request flows

A browser request such as /events maps to src/app/events/page.tsx. That page can read data on the server, render HTML, and compose components from src/components. If the page needs browser state—filters, modal state, or click handlers—put that interactive part in a small file marked "use client".

Rule of thumb: keep data access and secrets in Server Components or server-only modules; keep client components focused on interaction and pass them serializable data.

3. Run the project locally

  1. Install the exact toolchain. Use a Node.js version compatible with the installed Next.js version and pnpm 11. The lockfile is pnpm-lock.yaml, so pnpm should be the package manager.
  2. Install packages.
    pnpm install
  3. Configure a development database. Create a local PostgreSQL 15+ database and put its connection string in .env. Never point local work at production.
  4. Compile the database contract.
    pnpm contract:emit
    This updates prisma/schema.json and prisma/schema.d.ts from prisma/schema.prisma.
  5. Start Next.js.
    pnpm dev
    Open http://localhost:3000. Next’s Fast Refresh updates the page while you edit source files.

The useful commands are:

pnpm dev             # development server
pnpm lint            # ESLint
pnpm exec tsc --noEmit
pnpm contract:emit   # regenerate Prisma contract outputs
pnpm build           # production build
pnpm start           # serve a built app
pnpm check           # lint + types + contract + build
pnpm prisma migration status

4. Practical Next.js implementation

Example: add an events route

Create src/app/events/page.tsx. Because pages are Server Components by default, this is the natural place to query the database and render a first useful screen.

import { db } from "@/../prisma/db";

export default async function EventsPage() {
  // Start with a query for the current building once auth exists.
  // The project docs demonstrate the typed .where(...).first() API.
  const event = await db.orm.public.Event
    .where({ status: "scheduled" })
    .first();

  return (
    <main className="mx-auto w-full max-w-6xl p-6">
      <h1 className="text-2xl font-semibold">Events</h1>
      <p className="mt-2 text-muted-foreground">
        {event ? `Next booking: ${event.clientName}` : "No scheduled events yet."}
      </p>
    </main>
  );
}

In production, replace the placeholder filter with the authenticated admin’s buildingId. Check the generated contract and editor autocomplete for the exact collection operation when expanding from one record to a list.

Example: add a client-side filter

Do not turn the whole page into a client component just because a filter is interactive. Extract only the filter:

"use client";

import { useState } from "react";

export function EventFilter({ onChange }: { onChange: (value: string) => void }) {
  const [value, setValue] = useState("");
  return (
    <input
      value={value}
      onChange={(e) => { setValue(e.target.value); onChange(e.target.value); }}
      placeholder="Search client name"
      className="rounded-md border px-3 py-2"
    />
  );
}

5. Database workflow

prisma/schema.prisma is the domain contract. Current relationships are:

User ── optional belongs to ──> Building
Building ── has many ──> User
Building ── has many ──> Event
Event ── belongs to ──> Building

The UserRole enum distinguishes SUPER_ADMIN from BUILDING_ADMIN. pinHash indicates that PINs are intended to be stored as hashes, not plaintext; the dependency bcrypt is available for that job.

Safe schema-change loop

  1. Edit only prisma/schema.prisma; do not hand-edit generated schema.json or schema.d.ts.
  2. Emit the contract with pnpm contract:emit.
  3. Apply the appropriate Prisma migration/database command for the development database.
  4. Use the typed client from prisma/db.ts in server-side code.
  5. Run pnpm check before merging.
Security boundary: DATABASE_URL has no NEXT_PUBLIC_ prefix, so it must remain server-only. Never send it to a Client Component or expose it in browser code.

6. UI and styling workflow

globals.css imports Tailwind 4, animation utilities, and shadcn’s Tailwind layer. It also defines semantic CSS variables such as --primary, --background, and --destructive. Components should use these tokens instead of inventing one-off colors.

The existing Button wraps @base-ui/react/button and uses class-variance-authority for variants. A feature should consume it like this:

import { Button } from "@/components/ui/button";

<Button variant="default" size="lg">Create event</Button>
<Button variant="outline">Cancel</Button>

src/lib/utils.ts exports cn(), which combines conditional class names and resolves Tailwind conflicts. The @/* alias from tsconfig.json keeps imports stable while folders move.

7. Quality loop

Use a short feedback cycle after every vertical slice:

# while building
pnpm dev

# before considering the feature done
pnpm lint
pnpm exec tsc --noEmit
pnpm contract:emit
pnpm build

# or run the complete gate
pnpm check

Lint catches framework and accessibility issues, TypeScript catches contract mismatches, contract emission catches schema drift, and the production build catches bundling/server-client boundary problems.

8. A practical implementation order

The most coherent next milestone is one complete “event management” slice:

  1. Foundation Replace starter metadata and build a shared admin shell in layout.tsx.
  2. Read Add /events and render scheduled events from the typed database client.
  3. Auth Implement login with username + PIN verification, hash comparison with bcrypt, and a secure session strategy.
  4. Scope Enforce that a BUILDING_ADMIN can read/write only events for its buildingId; keep SUPER_ADMIN cross-building.
  5. Write Add a validated create-event form. Validate user input at the boundary with the existing Zod dependency, then persist on the server.
  6. Polish Add loading, error, empty, and not-found states for each route, then run pnpm check.
Definition of done for the first slice: an authenticated building admin can open an events page, see only their building’s bookings, create one valid booking, and receive a useful empty/error state when the database is unavailable.
